# 方案七：减少 Vercel 用量，并防止后台被暂停

状态：**已批准，第一节已完成**（2026-10-16）。Vercel 上最大的程序从约 97 MB 降到 29 MB。顺带修了一个问题：两期期刊不能再用同一个卷号和期号。原来的"搬到别的平台"需要信用卡，不可行，改为留在 Vercel，减少用量，并准备好备用办法。

## 为什么

Vercel 免费版每月只有 4 小时 CPU。超了不会扣钱（没有绑卡），但**后台会被暂停到下个月**：写稿、审稿、发布期刊、改横幅、读者投稿都会停。读者网站在 Cloudflare 上，照常能看。

## 一、把纸质版 PDF 搬到 Cloudflare（马上做）

生成 PDF 要启动一个完整的浏览器，是后台最耗 CPU 的操作，而且这个浏览器让每个部署大了 70 MB。

改成：

- **Cloudflare 构建网站时**，顺便把每一期纸质版生成 PDF，和网页一起放在 Cloudflare 上。读者下载 PDF 完全不经过 Vercel。
- 内容没变的旧期刊，直接沿用上次生成的 PDF，不重复生成，构建不会越来越慢。
- 万一 Cloudflare 上生成失败，网站照常构建，期刊页改为链接到一个**可直接打印的网页版**（读者可以用浏览器"打印 → 存为 PDF"），并在构建日志里写明原因。
- 后台里的"Proof the print edition"（发布前校对排版）保留，仍然在 Vercel 上打开，只是网页，不耗多少 CPU。可以用浏览器打印出来校对。
- Vercel 上不再有生成 PDF 的程序，每个部署小 70 MB。

## 一·五、图片放到 GitHub（2026-10-16 批准并完成）

- 上传的图片先存进**私有**仓库（草稿），只有登录后台的人能看到。
- 每次重建网站前（发布期刊、撤稿、Rebuild site），系统把已发布内容用到的图片复制到**公开**仓库，读者从 GitHub Pages 看图。没发布的图片永远不会进公开仓库。
- 撤稿后，那篇稿件独有的图片从公开仓库删除，并清空公开仓库的历史记录。（之前已经被缓存或 fork 的副本收不回来，所以敏感照片要在签字环节拦下。）
- 如果图片复制失败，网站不会重建，后台会提示原因，点 Rebuild site 重试。这样网站上永远不会出现坏掉的图片。
- 读者看图不占 Vercel 的流量，也不需要 Vercel Blob。

## 二、提前发现、及时处理

- Vercel 会在用量到 50%、75%、100% 时发邮件提醒。请确认 Vercel 账号的邮箱能收到。
- 每周看一眼 Vercel 的 **Fluid Active CPU**：一周不到 40 分钟，一个月就不会超。
- 如果某个月快用完了：先少用后台里耗资源的东西（比如反复点 Rebuild），把发布期刊集中安排。

## 三、真被暂停了怎么办（备用办法，以后再做）

如果用量实在不够，再做下面任一项（需要时单独写方案）：

- **首选：你的旧 Mac（13 寸 Intel）+ Cloudflare Tunnel。** 你有自己的域名，所以可以用 Cloudflare Tunnel 给它一个固定地址（如 `newsroom.你的域名`），免费、无限制，不需要信用卡。Mac 当主力、Vercel 当后备，两边连同一个数据库，随时可以切换。（2026-10-16 决定：先继续用 Vercel 观察，实在不够再做。）
- **学校里一台一直开着的电脑 + Cloudflare Tunnel**：同上。
- **找学校或社团出钱**：每月几美元就能彻底解决。

## 需要你做的

- 这次改动完成后，在后台点一次 **Rebuild site**，让 Cloudflare 生成现有各期的 PDF。
- 确认 Vercel 账号的邮箱能收到用量提醒。
